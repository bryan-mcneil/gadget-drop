Plan 04 (Price-Truth MCP, `feature/price-truth-mcp`) stands up `laravel/mcp` v0.8.2 at `POST /mcp`. Facts verified against vendor source in the 4.1 review — treat as confirmed-safe; do not re-flag in 4.2–4.4 reviews.

**Why:** these were plausible-looking BLOCKER candidates that turned out correct after reading `vendor/laravel/mcp/src`; re-flagging wastes a review cycle.

**How to apply:**
- **CSRF exclusion is real and safe.** `Mcp::web()` (Registrar.php) registers the POST route via `Route::group([], routes/ai.php)` with NO `web` group — no session/CSRF/VerifyCsrfToken. Package adds GET/DELETE→405 handlers + `ReorderJsonAccept`/`AddWwwAuthenticateHeader` middleware. Read-only + throttled ⇒ token-less POST is intended. Don't flag "missing CSRF".
- **Two-limit throttle with distinct `by()` keys is correct, not redundant.** `ThrottleRequests::handleRequestUsingNamedLimiter` computes the counter key as `md5($limiterName.$limit->key)` (or `$limiterName.':'.$limit->key` unhashed). Two `Limit`s in one named limiter that share `->by($request->ip())` would collide into one counter. The `mcp` limiter deliberately uses `mcp-min:`/`mcp-day:` prefixes so the 30/min and 300/day counters stay independent. This distinct-key trick is REQUIRED whenever a named limiter returns multiple Limits keyed off the same value.
- **Route caching:** `McpServiceProvider::registerRoutes` early-returns when `routesAreCached() && !runningInConsole()`, relying on the cache built during `route:cache` (which runs in console). This is the standard pattern — Phase 4.4's `route:cache` rehearsal is the right place to verify Livewire+MCP both survive; not a 4.1 concern.
- **Middleware order gotcha:** in `routes/ai.php` the array is `['throttle:mcp', McpCacheControl::class]` — throttle is outer, so a 429 short-circuits before `McpCacheControl`, and throttled responses lack `Cache-Control: no-store`. Harmless (POSTs aren't CDN-cached; 429s carry no price data) but if honesty-header coverage on error responses ever matters, McpCacheControl must come first.
- **Instructions link `#deal-verdicts`:** the server instructions string points at `how-we-review#deal-verdicts`, but `resources/views/public/how-we-review.blade.php` has no `id="deal-verdicts"` anchor yet. Plan 4.3 extracts the methodology partial — ensure the anchor lands then (or the fragment stays dead). RESOLVED in 4.3: anchor now lives in the shared partial `public/partials/deal-methodology.blade.php` (`id="deal-verdicts"`), included by how-we-review AND rendered-then-stripped-to-text by the `methodology` MCP resource — single copy, can't fork.

**Phase 4.2–4.4 confirmed-safe (verified 2026-07-22, combined review):**
- **No per-tool try/catch, by design — but prod-only-safe.** Tools handle EXPECTED errors explicitly (notTracked, exactly-one-identifier, length caps) and let UNEXPECTED throwables fall through to the package's global handler at `Server.php:213` (Throwable catch — NOTE the Build Log mis-cites `:211`, which is the JsonRpcException catch). That handler `report()`s then returns a calm generic `-32603 "Something went wrong..."` ONLY when `app.debug === false`; when APP_DEBUG=true it RE-THROWS (500 + stack trace). So plan 4.2 step-4's "every tool: try/catch → calm message, never a stack trace" is satisfied in prod (debug off) but NOT in a debug env. Acceptable; the gap is a debug-env-only stack trace. If re-reviewing, this is a WARN-not-BLOCKER (prod outcome matches intent) — but it should be documented in the Build Log, and it currently isn't.
- **Middleware chain `throttle → McpCacheControl → McpPayloadCap → McpUsageMeter`.** McpCacheControl is OUTER of the cap/meter, so the 413 payload-cap body still carries `no-store` (tested). McpUsageMeter counts AFTER `$next` and is INNERMOST, so it only counts requests that pass throttle+cap (oversized/throttled never counted — tested). Meter counts `method==='tools/call'` only, sanitizes the client-supplied `params.name` to `[a-z0-9_-]`, 40 chars, on the default (db in prod) cache store via `Cache::add`+`increment` in a try/catch (broken cache never 500s the endpoint). Confirmed-safe.
- **McpPayloadCap caps `params.arguments` (json_encode) at 1024 bytes only** — not the whole JSON-RPC envelope. Outer bound is PHP post_max_size. Plan-scoped to tool args; don't flag the envelope gap.
- **DealsFeed extraction is a verbatim move.** `DealsController::buildFeed()` → `App\Support\DealsFeed::{get,build}` with `MIN_DROP_PCT`/`MAX_ENTRIES` re-exposed as `@deprecated` aliases on the controller (existing view/test refs stay valid). Same `deals.feed` 1h cache + defensive try/catch→live-compute; PriceIntel::flush still busts it. `list_tracked_deals` and `/deals` now share it. Behaviour-preserving (suite green). Don't re-flag as a shape change.
- **No raw amazon.com in any tool response** — confirmed by a 4-tool sweep test; affiliate URLs are all `route('affiliate.redirect')`; ASIN is exposed as a bare identifier (not a URL), which is fine.
